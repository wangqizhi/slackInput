# 游戏坐标与战斗状态监控可行性研究

研究日期：2026-09-22；对应版本：0.7.1。本文仅为方案，不新增内存监控、地址扫描或挂机执行代码。

## 结论

**可以做到，但需要逐款游戏、逐个版本适配，不能只选进程就自动知道坐标和战斗状态。** 在能够取得读取权限、且数据存在于本地进程的前提下，可以周期读取人物坐标、场景标识、战斗阶段等状态，再用状态变化驱动有限的按键宏。实现难点主要是字段语义和生命周期验证，而非读取 API。

建议先做一个离线单机游戏的只读状态面板，验证稳定后再考虑挂机闭环。第一阶段优先识别「探索 / 战斗 / 结算 / 加载 / 未知」，坐标其次；只会跑固定按键序列还不足以可靠挂机。本文未读取真实游戏内存，没有确认任何具体地址、偏移、坐标类型或战斗枚举值。

Windows 提供 `ReadProcessMemory`，需要 `PROCESS_VM_READ` 权限，并应检查成功标志和实际读取字节数；跨入不可读区域会失败。此 API 只能提供字节，不解释游戏含义。[Microsoft：ReadProcessMemory](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-readprocessmemory)

## 当前项目可复用的部分

- `src/trainer/native.rs` 已使用 ReadProcessMemory，并具有进程创建时间验证、模块处理等基础设施。这证明项目已有 Windows 内存 API 接入能力，不证明某款游戏的监控字段已被定位。
- `src/trainer/profile.rs` / `config.rs` 有版本化数据格式和按游戏适配的基础。注意现有 `source_sha256` 指向导入来源，不能直接当作游戏 EXE 的版本指纹。
- `assets/trainers/digimon-execution.json` 有 battle HP/SP 等修改器执行参数，但它们服务于修改路径，不能由此推断有稳定的「正在战斗」字段或人物坐标地址。不得把 hook 上下文偏移当作独立可读指针链。
- `src/main.rs` 已有绑定代数和反作弊锁，可用来拒绝跨会话旧结果。
- `src/macros.rs` 已有可取消的串行宏执行器，但当前宏发送给前台窗口，没有状态订阅、游戏焦点门控或挂机状态机。接入监控后的联动属于后续开发。

**不要直接复用修改器的高权限 Process 句柄。** 只读监控单独申请 `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION`；若用等待函数检测进程结束，再加 `SYNCHRONIZE`。不申请写入、分配远程内存或暂停权限。[Microsoft：进程访问权限](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights)

## 数据来源选择

| 方式 | 可行性与限制 | 建议 |
| --- | --- | --- |
| 官方 Mod / 遥测 / 日志接口 | 如果存在，往往有明确字段含义；可提供事件，但取决于游戏开放程度 | 优先核查具体游戏官方接口 |
| 外部进程只读内存 | 可读到本地状态；需要版本适配、地址定位、结构验证 | 无官方接口时的主要候选 |
| 画面识别 | 不依赖地址，能判定部分菜单/战斗 UI；遮挡、分辨率和动画影响准确率 | 作为状态校验或后备，坐标精度较低 |
| 注入 DLL / 修改指令来暴露地址 | 增加侵入性和维护成本，与只读监控目标不同 | 本方案不采用 |

以上是工程评估，不是对具体游戏兼容性的承诺。服务器权威状态可能不在客户端，客户端也可能仅有显示缓存、预测或延迟副本。

## 如何定位与验证字段

在明确支持的本地测试环境、固定游戏版本中进行人工受控观察。记录游戏 EXE 哈希、模块版本、架构、存档和操作轨迹，形成可重复的测试样本。

### 人物坐标

先验证静止、沿单一方向移动、转身、跳跃、传送和地图切换时的候选数据变化。坐标可能是 float32、float64、整数网格或相对变换；不能默认连续三个浮点数就是 XYZ。需要区分玩家、镜头、队友、目标及显示用平滑坐标。

验收至少包括：静止稳定、往返运动方向一致、镜头单独旋转时不冒充玩家位移、换地图后旧对象失效、重新载入存档和重启后仍能重新定位。记录坐标系、单位、地图 ID 与合理范围。位置跳变不自动解释为传送，可能是换场景或读取不一致。

### 战斗状态

分别观察探索、遭遇过渡、回合等待、技能动画、胜利、奖励结算、逃跑、死亡和加载。不能仅凭 HP 非零或战斗对象指针存在判定正在战斗：缓存可能在结算后继续存在。

优先验证明确的状态枚举或场景状态字段；若不存在，结合两个以上独立信号推导，并将信心不足的结果置为 Unknown。数值与枚举映射必须通过重复操作验证，不能凭字段名称猜测。

### 地址稳定性

优先级为：已验证模块基址 + RVA、可验证的指针链、最后是绑定时执行的有界特征扫描。RVA 只是定位入口，不保证指针指向的对象长期有效。ASLR、堆分配、场景切换和更新都会改变地址或结构。

适配文件记录游戏指纹、模块名、定位规则、指针位宽、解引用顺序、字段类型、范围和校验条件。特征必须唯一且经过二次验证；零命中、多命中或版本不匹配时拒绝启用，不能猜一个地址继续执行。不采用跨版本的裸绝对地址。

## 建议架构

```text
绑定身份（PID + 创建时间 + 绑定代数 + 游戏指纹）
    → 只读适配器（定位与字段校验）
    → 后台采样器（读取、有效性和时间戳）
    → 状态解释器（去抖、转换、Unknown）
    → 只读面板与诊断日志
    → [后续] 有限状态机 → 可取消宏执行器
```

UI 线程只接收最新快照。建议先以 10 Hz 采样少量已知字段，按实际效果调整；不要每轮扫描全进程。VirtualQueryEx 可用来检查内存区域状态和保护属性，但检查后页面仍可能变化，不能代替读取时的错误处理。[Microsoft：VirtualQueryEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex)

建议快照结构包含：绑定代数、单调时间戳、适配器版本、地图 ID、可选坐标、战斗阶段、有效性原因。读取不完整、空指针、NaN、范围错误、身份变化、进程退出一律产生 Unknown；旧快照仅可在 UI 以过期样式展示，不能驱动动作。

多次 ReadProcessMemory 不构成原子快照。优先一次读取小的相邻结构；可读取前后对象标识/帧计数并比较，不一致就丢弃样本。没有一致性标记时采用合理性校验并容忍 Unknown，而不是暂停游戏获取一致性。

初始工程参数（需实测，不是 Windows 保证）：状态连续 3 次一致才接受变化；超过 500 ms 没有新有效数据时暂停自动动作；连续失败采用退避，恢复后要求重新确认运行。进程重启、绑定切换或版本改变清空全部地址缓存和状态历史。

## 为挂机练级预留的闭环

后续以有限状态机实现，不让宏自发无限循环：

| 状态 | 允许动作 | 退出/保护条件 |
| --- | --- | --- |
| 未知、加载、暂停 | 无 | 等待重新确认且数据稳定 |
| 探索 | 有限次数的巡逻/交互宏 | 遭遇战斗立即取消探索宏；无位移超时暂停 |
| 战斗 | 适配游戏的有限战斗宏 | 等待结算；战斗超时暂停 |
| 结算 | 一次确认宏 | 回到探索再开始下一轮 |
| 死亡、背包满、异常弹窗 | 无 | 提示用户处理 |

仅在目标游戏窗口处于前台、身份匹配、用户明确开始且数据有效时执行。切走游戏、反作弊命中、进程退出、锁屏/无法确认焦点或紧急停止时取消并释放输出键。重新聚焦不自动恢复挂机。设置单轮和总时长上限、动作冷却及重复事件去重，避免同一个战斗状态每帧触发宏。

只读坐标不能直接实现可靠导航：还需要朝向、碰撞、地图/路径、卡住检测等。建议第一版只验证状态驱动的战斗与结算，不承诺通用自动寻路。若游戏有原生自动战斗，先研究是否只需监控阶段并确认结算。

## 反作弊与权限边界

沿用「检测命中即停用」原则，不研究绕过、隐藏或关闭保护。当前项目仅在绑定有效游戏时约每 2 秒检查有限的 EAC/BattlEye 进程名；没有命中不等于没有反作弊。后续监控建议在检测未完成、结果过期或扫描失败时不开始自动动作，已经命中的锁不能被扫描失败清除。

只读访问也可能被目标拒绝；权限错误应给出状态并停止，不自动提权或采用替代注入。对联网游戏及服务器状态不作挂机可用性承诺。

## 分阶段落地与验收

1. **适配研究**：选定游戏 EXE 版本和本地模式，确认有无官方接口。产出字段含义、定位证据和重启/换场景验证记录。
2. **只读面板**：先显示战斗状态、地图 ID、坐标和更新时间；完全不联动宏。验收多次重启/读档、全部战斗阶段、解绑、进程退出和读失败。
3. **稳定性测试**：至少 30 分钟观察，统计采样耗时、失败率、状态误判和过期快照；测试版本不匹配、指针失效、权限拒绝、反作弊命中。失败不得仍显示正常有效数据。
4. **后续可选联动**：先用自建模拟进程与状态序列测试取消、去重、超时和焦点门控，再在目标游戏手动监督短时试运行。单独提出实现任务后才开发。

是否进入第三、四阶段由前一步证据决定。最大不确定性是具体游戏字段定位，不能仅凭已有修改器给出可靠工期。当前无需额外修改运行代码；本文件就是本轮研究交付。
